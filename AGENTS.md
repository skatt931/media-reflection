# Codex project instructions

- Мова спілкування і specs: українська. Технічні терміни й code identifiers можна англійською.
- Це етап обговорення та архітектури. Не створювати production code, інфраструктуру чи підключення до сервісів, поки користувач явно не попросить.
- Перед кожною архітектурною рекомендацією прочитати `README.md`, `docs/conversation-context.md` та всі `specs/*.md`.
- Розділяти **затверджені вимоги**, **пропозиції** та **відкриті рішення**.
- Критерії: найменша постійна вартість, приватність нотаток, найменша експлуатаційна складність, хороша мобільна UX.
- Не вважати, що GitHub це повноцінна БД, або що login UI достатньо захищає статичний сайт.
- Уточнювати точкові технічні рішення перед впровадженням і оновлювати `specs/07-decisions.md` після узгодження.

## Субагенти (`.claude/agents/`)

Запускати відповідного агента, не робити цю перевірку самостійно:

- Нова фіча, архітектурна пропозиція чи зміна поведінки → `spec-guardian` до написання коду.
- Зміни в `src/miniapp/`, `src/mcp/`, `src/groq.ts`, `src/voice.ts`, експорті (`src/export-package.ts`, `src/vault.ts`, `scripts/export*`), `metadata.ts`/`links.ts` або в обробці щоденника й ідей → `privacy-security-reviewer`.
- Зміни в `src/`, `scripts/` або нова поведінка, що потребує тестів → `bot-tester`.
- Зміни в `miniapp/src/` чи `design/` → `miniapp-ui-reviewer`.
- Перед релізом (зміни в `deploy/`, `.github/`, міграціях, `miniapp-dist/`, `.env.example`) → `deploy-ops-checker`.

Рев'ю-агенти лише читають: застосовувати їхні правки й оновлювати specs можна тільки після згоди користувача. Незалежні рев'ю запускати паралельно. Готові процедури: `/review-branch` і скіл `feature-build`.
