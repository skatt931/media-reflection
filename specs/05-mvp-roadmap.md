# 05. MVP та етапи

## Етап 0 — уточнення дизайну (зараз)

- Підтвердити source of truth, доступну інфраструктуру та цільовий спосіб синхронізації Obsidian.
- Визначити мінімальну schema і правила статусів.
- Обрати: n8n на VPS чи serverless endpoint, виходячи з реальної вартості.
- Погодити критерії успіху: чи бот додає користь без рутини.

## Етап 1 — робочий MVP

1. Створити приватного Telegram-бота і whitelisting Telegram user ID.
2. URL/text ingestion із підтвердженням; зберігати raw і нормалізовані поля.
3. Базова класифікація: правила для відомих доменів, AI fallback для тексту; `unknown`, якщо невпевнено.
4. Durable store (n8n Data Table або DB).
5. Щоденний дайджест о 08:30 (налаштований TZ), інтерактивні кнопки; відповіді зберігаються з прив'язкою до media ID.
6. Простий експорт JSON/Markdown, щоб ніколи не втратити дані.
7. Логи помилок, retry, backup.

**Acceptance demo:** надсилання URL увечері → вранці приходить повідомлення → користувач лишає оцінку/коментар або пропускає → інформація зберігається після рестарту.

## Етап 2 — Obsidian/GitHub

- Запис/експорт у приватний GitHub repo з Markdown/YAML.
- Налаштування Obsidian vault; перевірити desktop та iOS sync, конфлікти.
- За потреби voice note STT та metadata enrichment.

## Етап 3 — персональний web UI

- React/TypeScript app: список і картки, type/status/rating/tag filter, full-text search.
- Захищений доступ до приватних даних.
- Перехід із вебкартки до Markdown-нотатки за id.

## Етап 4 — аналітика

- Тижневі підсумки, відстеження смаків, ручні колекції, можлива семантична навігація.

## Антицілі MVP

- Не робити одночасно декілька різних баз істини.
- Не будувати власну auth platform, якщо доступний готовий безпечний механізм.
- Не імпортувати всі Spotify/YouTube/Instagram історії без потреби.
- Не запускати локальну LLM, якщо маленький API-запит простіший.
